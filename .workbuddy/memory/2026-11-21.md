## 检索升级 L1：search_document 改为跨文件 + 多关键词 + 候选卡片

背景：用户提出上向量库做语义检索、加倒排索引。分析后判定其规模（3 份文档 / 26 万字）
上向量库属于过度工程，且会破坏"离线可用"；决定先做 L1（不加任何依赖）。

改动：
- `app/tools/doc_tools.py`
  - 签名 `search_document(keyword, name="")`：name 由必填改为可选，默认搜全部资料。
  - `_terms()` 按空格/中英标点切词做 OR；`_bigrams()` 中文两字切，仅整词零命中时降级。
  - `_score()` 以"命中不同词数"为主权重（3.0/词），重复次数 0.4 次权重，全覆盖 +1.5。
  - `_snippet()` 只截命中处 110 字（前后各留 24 字），候选卡片不含整段。
  - `_scan(need_ratio=)`：模糊那一遍要求覆盖率 60%（`FUZZY_COVERAGE`），
    否则"不存在的词甲乙丙"会靠"存在"撞出 41 段假候选（实测踩到，已修）。
  - 返回最多 3 段（`MAX_CANDIDATES`），附可直接照抄的 `read_document(...)` 调用。
- `app/agent.py`：策略行同步为"默认搜全部资料、多关键词空格分隔"。
- `README.md` 第 6 条补充 search 的接口契约与覆盖率闸门。
- `tests/test_docs.py` 新增 `TestSearchScopeAndRanking` 8 个用例（跨文件/OR/排序/片段长度/
  模糊标注/假命中拒绝/name 不存在/keyword 必填）。

效果（真实语料实测）：全库扫描 0.8–1.5ms；单次返回约 640 字符（约 450 token）；
最相关段落能稳定排到 #1。旧路径（搜不到 → 顺序读完 15 万字案例集）约 10 万 token。

## 第三轮：「思考过程」里的最终回答去重

用户问："思考过程里的最终回答和下面的答案一致，会重复消耗 token 吗"。
结论：**不会**。token 只由 `usage` 决定（`agent.py:262` 每步加一次），界面 `markdown()`
是本地渲染；流式阶段回调的是累积串且 UI 用覆盖而非追加，所以连视觉重复都不存在。
真正的"重复计费"是**历史回放**：一轮 43,408 token 的回答结束后，`messages` 留 14,722 字
（约 10.3k token，其中 tool 返回 10,879 字）会在之后每一轮重发。
另发现 `_make_conv_title`（ui_streamlit:85）每个新对话额外发一次请求且**不计入**
`session.tokens`，侧栏数字偏低。

只做了用户要的显示层去重（其余两项没动）：
- `app/ui_render.py`：删掉 `build_item` 的 `final` 分支（返回 None），模块 docstring 写明原因
  （答案已由界面渲染成气泡；再进面板还会被 MAX_BODY_CHARS 截断，两份内容对不上）。
  `_emit("final")` 保留，它是这一轮结束的信号，只是不再落成展示记录。
- `app/ui_streamlit.py`：**原本改过、已撤销**。当时担心"无工具调用的一轮 items 为空 →
  `to_markdown()` 返回 `_等待模型响应…_` 占位符 → 被当过程存进历史"，于是在落盘处加
  `if trace.items else ""`。实测（stub llm 只回 content）证明 items 恒为 `['step']`：
  `_emit("step")` 在每次 LLM 调用后、任何 return 分支之前触发，所以永不为空。
  该判断防的是不存在的情况，属于隐性回退，已还原成 `trace.to_markdown()`。
  教训：先验证"是否真会为空"，再决定要不要兜底。
- `README.md` 样例：`[最终回答]` 移出代码块，说明答案在面板下面。
- `tests/test_week4.py`：`test_final_warning_error` 拆成 `test_final_does_not_enter_panel`
  （断言 is None）+ `test_warning_and_error`；`test_collects_in_order` 改为断言 final 不进 items。

## 第四轮：整合文档切分策略（只梳理，未改代码）

把散在四个文件里的切分逻辑汇总成"条件 → 规则"两张表，关键结论：
- **抽取单位 ≠ 块边界**。PDF 页标记、docx 表格、xlsx 工作表都只是抽取时的结构，
  最终一律被 `split_chunks` 按 2000 字重切，页和表都可能被劈开。
  唯一例外：`read_file` 读 .pptx 走 `describe_pptx`，页为原子、累积 ≤1600 字/片。
- 断点不是优先级：`max(rfind("\n"), rfind("。"), rfind(". "))` 取最靠后的一个；
  英文单 "." 不认，必须 ". "。位置需严格 > `size*0.6`，故块长 1201–2001 或 2000。
- 同一 .csv 两入口行为不同：上传 → dataset 表（不切块）；`read_file` → 文本切 2000 字。
- 截断只在入库时做一次（200,000 字），`read_document` 返回再受 `MAX_OBS_CHARS=4000` 限制。
- 未新建文档文件（用户只要表格），代码位置：readers.py:138/389、config.py:39-41、
  doc_tools.py:107/252、file_tools.py:69、pptx_tools.py:1076。

## 第五轮：切块正确性核查（未改代码）

432 组（6 种文本形态 × 9 种长度 × 8 种 size）跑不变量：**无丢字、无重复、无越界、
无空块（纯空白输入除外）、断点逻辑正确**。逐行日志 37 个非末块全部落在换行处，
中文/英文句号文本分别 4/5、8/9 个非末块落在句号，其余为刚好满 2000 的硬切。

唯一硬缺口：`split_chunks(size<=0)` 会死循环（`end=start` 且 `while start < total` 永真）。
生产路径不可达（`DOC_CHUNK_CHARS=2000` 常量），但函数在 `__all__` 里导出，测试也会传 size。
未修——用户没要求动代码，且加 `max(1,size)` 属于静默修正，与"不要隐性回退"的偏好冲突。

三个"不是 bug 但影响回答质量"的边界：
1. 无断点时硬切，会切断句子、表格行、JSON/日志单行；
2. `search_document` 是段内匹配且块间无重叠，关键词横跨两块交界时必然漏检（miss 型错误）；
3. PDF 页标记、docx 表格、xlsx 工作表都不是块边界，2000 字可把页/表劈开。
