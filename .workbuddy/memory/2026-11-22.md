### 踩到的坑（下次直接照这个配）

1. **Judge 的 `max_tokens` 不能给 1200。** 长表格答案能拆出 15 条声明，
   JSON 在 midpoint 被截断，64 条里 22 条 fallback。改 3000 后归零。
2. **`is_refusal` 必须也算拒答。** Judge 偶尔给 `is_refusal=true, noncommittal=false`，
   只按 noncommittal 判会让"资料里没有"拿到 0.9 的相关性。
3. **`pass` 只按计划书三条件**（无矛盾 + 忠实度≥阈 + 相关性≥阈）。
   早先额外要求 `unsupported==0` 会把 0.94 忠实度的答案全压成 warn，通过率失去意义。
4. **否定性断言要按检索记录判**（"另两份资料不涉及"），否则诚实说明反被判无依据。
5. **终端中文表格要用 east_asian_width 算宽度**，`len()` 对齐会错行。

### 实测结论（64 次问答 / 16 用例 × 4 配置）

| 配置 | 忠实度 | 相关性 | pass |
|---|---|---|---|
| baseline（无改写） | 0.935 | 0.700 | 15/16 |
| basic_rewrite | 0.949 | 0.687 | 13/16 |
| colloquial | 0.918 | 0.696 | 13/16 |
| cross_lingual | 0.990 | 0.676 | 12/16 |

整体：声明 680 条，支持 645 / 无依据 35 / **矛盾 0**；11 条 warn 全部可解释
（3 条是派生指标或常识补充被判无依据，8 条是开放式长答案的逆向相似度偏低）。

**前置改写没有提升忠实度或相关性**（±0.02 属 Judge 噪声）：检索召回本来就够，
改写主要省步数。这个负结论值得保留在报告里，别只报好数字。

### 已知指标边界

- 逆向问题余弦对"开放式长答案"天然偏低（cross_source 类 ~0.64），不能当作答错。
- 可换算的派生指标（占比、单均）有时被判无依据：Judge 严格度问题，不是模型编造。
- Judge 温度 0 仍有波动：同一快照重跑，忠实度摆动约 ±0.03。

## agent.py 架构梳理（只用图表解释，未改代码）

`app/agent.py` 353 行：`make_system_prompt` 四段条件拼装（~110 行）、
`Agent.__init__` + `_emit/_stop/update_system_prompt`（~45 行）、
`ask()` 主循环（~136 行，其中循环骨架 70 行）、前置改写与上下文注入（~60 行）。

- 唯一被框架接管的只有循环骨架。若换 LangChain，353 → 约 280 行（省不到三成），
  而 prompt 拼装、事件映射、按单问计 token 预算、重复调用检测、session_key 隔离
  一样都要自己写。结论：不换；未来要做多 Agent / human-in-the-loop 看 LangGraph。
- `app/session.py` 的 `reset/save/load/to_dict` 在 `app/` 内**无任何调用者**
  （持久化实际走 `chats.py`，恢复时由 `ui_streamlit.py:415` 用 `chat.stats` 重新构造）。
  可安全删除，测试也不依赖。

## 恢复历史对话的链路（易踩点）

1. 侧栏点击 → `_forget_local_state(chat_id)`：先 `_persist_chat(force=True)`，
   再 `unbind_dataset` / `clear_documents` / `uploads.discard`，**换新 sid**，
   `ss.session = Session()` 清空，最后写 URL `?c=<id>` + `st.rerun()`。
2. 重跑时 `_restore_chat()`：`restored == chat_id` 直接返回（防每帧重复读盘）→
   `chats.load(id)` → 重建 `Session(messages, stats)` + `_make_agent` →
   `dt.use_dataset(ss.sid)` + `bind_dataset(frame, key=sid)`，并设 `ss.bound`
   让后面 `_apply_dataset` 不再走 `_bind_table`（那条路会清对话）。
   表回不来时 `ss.table_id = ""`（必须是空串，None 会触发自动选表）。
3. **已知细节**：恢复后 `messages[0]` 是当时存下的旧 system prompt，
   而 `ask()` 只在首条不是 system 时才插入，所以 `_make_agent(ss.session, _prompt_text())`
   传进去的新 prompt 不生效。想让恢复后按当前资料刷新，只能显式调
   `_refresh_prompt()`（内部走 `update_system_prompt`，会替换 `messages[0]`）。

「上下文」在这个项目里是三套东西，别混：对话上下文 = `Session.messages`；
数据上下文 = `contextvars` 的 `_ACTIVE`（工具按 sid 取连接，不在 messages 里）；
改写上下文 = `build_context` 现采（messages 摘要 + 表字段 + 文档目录）。

## PDF 图片能否进模型（结论已实测，别再用旧印象答）

- **模型侧没问题**：实测 `deepseek-chat` + `image_url` 图片块返回 200，答对了图内容；
  响应 `model` 字段是 `deepseek-flash`——即 `deepseek-chat` 已被路由到
  DeepSeek-V4.1-Flash-1017。官方模型表只剩 `deepseek-flash`（Vision ✓）和
  `deepseek-v4-pro`（Vision ✗）。`.env` 里的 `deepseek-chat` 建议改成 `deepseek-flash`，
  免得别名下线。图片支持 `user` / `system` / `tool` 消息，**assistant 里放图会 400**。
- **管道侧没送**：`readers.py:225` 只 `page.extract_text()`，图片字节从未进入 `Doc`；
  `doc_tools.py:127` 返回 `str` 并截断到 `MAX_OBS_CHARS`(4000)；
  `agent.py:335` 组装 `{"role":"tool","content": observation}` 纯字符串。
  全项目 `app/` 无一处 `image_url` / `data:image`。
- **`llm.py` 无需改动**：`json.dumps(payload)` 对 messages 格式无关，数组 content 原样透传。
  要接图，改动只在 readers（抽图/渲染页）+ Doc 增加图片字段 + tool 返回数组，
  另需替换按字符截断的 `MAX_OBS_CHARS`。成本：单图 ≤1024 token，应做"按需看图"。
- 教训：问模型能力必须查官方文档 + 实测，不要凭训练印象断言。
